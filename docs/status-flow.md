## 1. Authentication Flow — การล็อกอิน

ระบบใช้ CMU OAuth 2.0 ผ่าน Microsoft Azure AD เชื่อมต่อกับบัญชี CMU Account ของมหาวิทยาลัยเชียงใหม่

### 1.1 ลำดับการล็อกอิน

```
 นักศึกษา / เจ้าหน้าที่                ระบบ                     Microsoft Azure AD           CMU MIS API
 ─────────────────               ─────                    ─────────────────          ─────────────
       │                          │                              │                         │
       │  1. กดปุ่ม "เข้าสู่ระบบ"    │                              │                         │
       │─────────────────────────►│                              │                         │
       │                          │  2. สร้าง CSRF state         │                         │
       │                          │     + set cookie             │                         │
       │                          │  3. Redirect →               │                         │
       │                          │─────────────────────────────►│                         │
       │                          │                              │                         │
       │                          │     4. ผู้ใช้กรอก             │                         │
       │                          │     CMU Account              │                         │
       │                          │◄─────────────────────────────│                         │
       │                          │  5. Redirect กลับพร้อม code  │                         │
       │                          │──────────────────────────────►│                         │
       │                          │  6. Exchange code → token     │                         │
       │                          │◄──────────────────────────────│                         │
       │                          │  7. Access Token              │                         │
       │                          │                                                          │
       │                          │  8. เรียก Basic Info API ──────────────────────────────►│
       │                          │◄───────────────────────────── 9. ข้อมูลส่วนตัว ──────────│
       │                          │     (name, email, studentId,                         │
       │                          │      cmuItAccount, accountType)                      │
       │                          │                                                          │
       │                          │  10. ตรวจสอบ Role                                        │
       │                          │      อีเมลอยู่ในระบบ?                                     │
       │                          │      → ADMIN : STUDENT                                   │
       │                          │                                                          │
       │                          │  11. สร้าง/อัปเดต Profile                                │
       │                          │  12. สร้าง Session Token                                 │
       │                          │      (HMAC-SHA256)                                       │
       │                          │  13. บันทึก ActivityLog                                  │
       │                          │      (USER_LOGIN)                                        │
       │                          │                                                          │
       │  14. Redirect ตาม Role  │                                                          │
       │◄─────────────────────────│                                                          │
       │     STUDENT → /dashboard                                                          │
       │     ADMIN   → /admin/dashboard                                                    │
```

### 1.2 การตรวจสอบบทบาท (Role Detection)

| เงื่อนไข | บทบาทที่ได้ |
|---|---|
| อีเมลมีอยู่ในระบบ (Admin เพิ่มไว้ล่วงหน้า) | `ADMIN` (เจ้าหน้าที่) |
| อีเมลไม่มีในระบบ | `STUDENT` (นักศึกษา) |

### 1.3 ข้อมูลที่ดึงจาก CMU MIS API

| ข้อมูล | แหล่งที่มา | เก็บใน DB? |
|---|---|---|
| ชื่อ-นามสกุล, อีเมล, รหัสนักศึกษา | CMU Basic Info API | Yes — Profile |
| ข้อมูลวิทยานิพนธ์ (ชื่อ, ภาค, ระดับ, หลักสูตร) | Thesis API | No — ดึงแสดงผลเท่านั้น |
| สถานะนักศึกษา (กำลังศึกษา/ลาออก/พ้นสภาพ) | CMU MIS API | No — ดึงแสดงผลเท่านั้น |

## 2. RBAC — สิทธิ์การเข้าถึงตามบทบาท

ระบบควบคุมสิทธิ์ด้วย 2 ชั้น: Proxy (ระดับ route) + Layout Guard (ระดับหน้า)

### 2.1 สิทธิ์ตามบทบาท

| หน้า / ฟังก์ชัน | นักศึกษา (STUDENT) | เจ้าหน้าที่ (ADMIN) |
|---|:---:|:---:|
| หน้า Landing (`/`) | ✅ | ✅ |
| เข้าสู่ระบบ (`/login`) | ✅ | ✅ |
| แดชบอร์ดนักศึกษา (`/dashboard`) | ✅ | ❌ |
| ยืมเครื่องมือ (`/borrow`) | ✅ | ❌ |
| แดชบอร์ดเจ้าหน้าที่ (`/admin/dashboard`) | ❌ | ✅ |
| จัดการเอกสาร (`/admin/documents`) | ❌ | ✅ |
| รายชื่อนักศึกษา (`/admin/students`) | ❌ | ✅ |
| จัดการการยืม (`/admin/borrowing`) | ❌ | ✅ |
| ประวัติการใช้งาน (`/admin/activity-log`) | ❌ | ✅ |

### 2.2 การป้องกัน Route (Proxy Flow)

```
 ผู้ใช้เข้าถึงหน้าใดหน้าหนึ่ง
       │
       ▼
 Proxy ตรวจสอบ Session Cookie
       │
       ├── ไม่มี Session ──────────── หน้าสาธารณะ? (/, /login)
       │                                │
       │                           ├── ใช่ → แสดงหน้าปกติ
       │                           └── ไม่ใช่ → Redirect → /
       │
       └── มี Session
            │
            ├── STUDENT เข้า /admin/* → Redirect → /dashboard
            ├── ADMIN เข้า /dashboard, /borrow → Redirect → /admin/dashboard
            ├── ผู้ใช้เข้าสู่ระบบแล้วเข้า /login → Redirect → Dashboard ตาม Role
            └── สิทธิ์ถูกต้อง → แสดงหน้าปกติ
```

## 3. Document Status Flow — การจัดการเอกสาร

เอกสารเครื่องมือวิจัยที่นักศึกษาอัปโหลด ผ่าน 3 สถานะ: **รอตรวจสอบ → อนุมัติแล้ว / ปฏิเสธแล้ว**

### 3.1 State Machine Diagram

```
                      ┌──────────────────────────┐
                      │                          │
   นักศึกษา            │       PENDING            │
   อัปโหลด PDF        │      รอตรวจสอบ           │
  ───────────────►    └───────────┬──────────────┘
   + กรอกชื่อ                     │
     เครื่องมือวิจัย                │
                      ┌──────────┴───────────┐
                      │                      │
                 ┌────▼─────┐          ┌─────▼──────┐
                 │          │          │            │
                 │ APPROVED │          │ REJECTED   │
                 │อนุมัติแล้ว │          │ ปฏิเสธแล้ว   │
                 │          │          │            │
                 └────┬─────┘          └─────┬──────┘
                      │                      │
                      ▼                      ▼
               นักศึกษาดาวน์โหลด        นักศึกษาอัปโหลด
               ใบรับรอง PDF           ใหม่ได้ (เริ่มใหม่)
```

### 3.2 สถานะเอกสาร (Document Status)

| สถานะ | ชื่อไทย | สี Badge | คำอธิบาย |
|---|---|---|---|
| `PENDING` | รอตรวจสอบ | ส้ม (Amber) | เอกสารใหม่ที่รอเจ้าหน้าที่ตรวจสอบ |
| `APPROVED` | อนุมัติแล้ว | เขียว (Green) | เจ้าหน้าที่ตรวจสอบแล้ว นักศึกษาสามารถดาวน์โหลดใบรับรองได้ |
| `REJECTED` | ปฏิเสธแล้ว | แดง (Red) | เจ้าหน้าที่ปฏิเสธพร้อมเหตุผล นักศึกษาต้องอัปโหลดใหม่ |

### 3.3 รายละเอียดการเปลี่ยนสถานะ

| # | จาก | เป็น | ผู้ดำเนินการ | เงื่อนไข | Side Effects |
|---|---|---|---|---|---|
| D1 | — | `PENDING` | นักศึกษา | อัปโหลด PDF + กรอกชื่อเครื่องมือ | บันทึก ActivityLog (`DOCUMENT_UPLOAD`); ส่งอีเมลแจ้งเจ้าหน้าที่ |
| D2 | `PENDING` | `APPROVED` | เจ้าหน้าที่ | กดปุ่ม "อนุมัติ" ยืนยัน | set `reviewedBy`, `reviewedAt`; สร้าง Instrument (ถ้ายังไม่มี); บันทึก ActivityLog (`DOCUMENT_APPROVE`); **ส่งอีเมลแจ้งนักศึกษาเมื่อเอกสารทั้งหมดได้รับการอนุมัติแล้ว** |
| D3 | `PENDING` | `REJECTED` | เจ้าหน้าที่ | กดปุ่ม "ปฏิเสธ" + กรอกเหตุผล | set `reviewedBy`, `reviewedAt`, `adminNotes`; บันทึก ActivityLog (`DOCUMENT_REJECT`); **ส่งอีเมลแจ้งนักศึกษาทันทีพร้อมเหตุผล** |
| D4 | `PENDING` | (ลบ) | นักศึกษา | ลบเอกสารของตัวเองเท่านั้น | ลบไฟล์ PDF + ลบ record; บันทึก ActivityLog (`DOCUMENT_REMOVE`) |
| D5 | ทุกสถานะ | (ลบ) | เจ้าหน้าที่ | ลบได้ทุกสถานะ | ลบไฟล์ PDF + ลบ record; บันทึก ActivityLog (`DOCUMENT_REMOVE`) |

### 3.4 กฎที่เปลี่ยนแปลงไม่ได้ (Immutable Rules)

- `APPROVED` และ `REJECTED` เป็น **สถานะสุดท้าย** — เปลี่ยนสถานะต่อไม่ได้
- นักศึกษาลบเอกสารได้เฉพาะ **PENDING** ของตัวเองเท่านั้น
- เจ้าหน้าที่ลบเอกสารได้ทุกสถานะ
- "อนุมัติทั้งหมด" กระทบเฉพาะ **PENDING** เท่านั้น — APPROVED เดิมไม่ถูก approve ซ้ำ

### 3.5 Upload Flow (นักศึกษาอัปโหลดเอกสาร)

```
 นักศึกษาเข้าหน้า Dashboard
       │
       ▼
 กรอกชื่อเครื่องมือวิจัย + เลือกไฟล์ PDF (รองรับหลายฉบับพร้อมกัน)
       │
       ▼
 ระบบตรวจสอบ:
  ├── ไฟล์ต้องเป็น PDF เท่านั้น
  ├── ขนาดไฟล์ไม่เกิน 10 MB ต่อฉบับ
  └── ต้องกรอกชื่อเครื่องมือทุกฉบับ
       │
       ├── ข้อมูลไม่ถูกต้อง → แจ้งเตือน error เฉพาะแถว
       │
       └── ข้อมูลถูกต้อง
            │
            ▼
       แสดง Confirmation Dialog:
       "ยืนยันการอัปโหลดเอกสาร X ฉบับ?"
            │
            ├── ยกเลิก → กลับไปแก้ไข
            │
            └── ยืนยัน
                 │
                 ▼
            บันทึกไฟล์ลง uploads/{studentId}/
            สร้าง Document record (status = PENDING)
            บันทึก ActivityLog (DOCUMENT_UPLOAD)
                 │
                 ▼
            ส่งอีเมลแจ้งเจ้าหน้าที่:
              To: supapan.ch@cmu.ac.th
              CC: ampika.s@cmu.ac.th
              Subject: "แจ้งเตือน: นักศึกษาอัปโหลดเอกสารเครื่องมือวิจัย"
              ระบุ: ชื่อนักศึกษา, รหัส, รายการเอกสารที่อัปโหลด
                 │
                 ▼
            แสดง Toast "อัปโหลดสำเร็จ"
            รีเฟรชรายการเอกสาร
```

### 3.6 Approve Flow (เจ้าหน้าที่อนุมัติ)

```
 เจ้าหน้าที่เข้าหน้า /admin/documents หรือ /admin/students/[id]
       │
       ▼
 กดปุ่ม "อนุมัติ" บนเอกสารที่ status = PENDING
       │
       ▼
 แสดง Confirmation Dialog:
 "ยืนยันการอนุมัติ? นักศึกษาจะได้รับแจ้งทางอีเมล"
       │
       ├── ยกเลิก → กลับ
       │
       └── ยืนยัน
            │
            ▼
       อัปเดต Document:
         status → APPROVED
         reviewedBy → admin email
         reviewedAt → now
       สร้าง Instrument (ถ้าชื่อเครื่องมือยังไม่มีในระบบ)
       บันทึก ActivityLog (DOCUMENT_APPROVE)
            │
            ▼
       ตรวจสอบ: นักศึกษาคนนี้ยังมีเอกสาร PENDING เหลืออยู่หรือไม่?
            │
            ├── มี PENDING เหลือ → ไม่ส่งอีเมล (รอให้อนุมัติหมดก่อน)
            │
            └── PENDING หมดแล้ว → ส่งอีเมลแจ้งนักศึกษา:
                  To: อีเมลนักศึกษา
                  Subject: "แจ้งผลการพิจารณาวิทยานิพนธ์"
                  แจ้งว่าเอกสารทั้งหมดได้รับการอนุมัติแล้ว
                 │
                 ▼
            นักศึกษาเห็น status "อนุมัติแล้ว" ใน Dashboard
            นักศึกษาสามารถดาวน์โหลด "ใบรับรอง PDF" ได้
```

### 3.7 Bulk Approve Flow (เจ้าหน้าที่อนุมัติทั้งหมด)

```
 เจ้าหน้าที่กดปุ่ม "อนุมัติทั้งหมด" สำหรับนักศึกษาคนใดคนหนึ่ง
       │
       ▼
 แสดง Confirmation Dialog:
 "ยืนยันการอนุมัติเอกสารทั้งหมดของ [ชื่อนักศึกษา]?"
       │
       └── ยืนยัน
            │
            ▼
       ค้นหาเอกสารทั้งหมด: userId = นักศึกษาคนนั้น AND status = PENDING
            │
            ▼
       อัปเดตทุกฉบับ → APPROVED:
         - reviewedBy = admin email
         - reviewedAt = now
       สร้าง Instrument สำหรับแต่ละฉบับ (ถ้ายังไม่มี)
       บันทึก ActivityLog (DOCUMENT_APPROVE) ทีละฉบับ
            │
            ▼
       ส่งอีเมลแจ้งนักศึกษา 1 ฉบับ:
         To: อีเมลนักศึกษา
         Subject: "แจ้งผลการพิจารณาวิทยานิพนธ์"
         ระบุรายการเอกสารที่อนุมัติทั้งหมด
```

> **หมายเหตุ:** ถ้านักศึกษาเพิ่มเอกสารใหม่หลังจาก bulk approve แล้ว เอกสารใหม่จะเป็น `PENDING` และเจ้าหน้าที่ต้องอนุมัติใหม่อีกครั้ง

### 3.8 Reject Flow (เจ้าหน้าที่ปฏิเสธ)

```
 เจ้าหน้าที่กดปุ่ม "ปฏิเสธ" บนเอกสารที่ status = PENDING
       │
       ▼
 แสดง Reject Dialog:
 "กรุณาระบุเหตุผลในการปฏิเสธ" (textarea — จำเป็นต้องกรอก)
       │
       ├── ยกเลิก → กลับ
       │
       └── กรอกเหตุผล + ยืนยัน
            │
            ▼
       อัปเดต Document:
         status → REJECTED
         reviewedBy → admin email
         reviewedAt → now
         adminNotes → เหตุผลที่กรอก
       บันทึก ActivityLog (DOCUMENT_REJECT)
            │
            ▼
       ส่งอีเมลแจ้งนักศึกษาทันที:
         To: อีเมลนักศึกษา
         Subject: "แจ้งผลการพิจารณาวิทยานิพนธ์"
         ระบุ: ชื่อเอกสาร + เหตุผลที่ปฏิเสธ
            │
            ▼
       นักศึกษาเห็น status "ปฏิเสธแล้ว" + เหตุผลใน Dashboard
       นักศึกษาสามารถอัปโหลดเอกสารใหม่ได้
```

### 3.9 Remove / Delete Flow

```
 ผู้ใช้กดปุ่ม "ลบ" บนเอกสาร
       │
       ▼
 แสดง Confirmation Dialog:
 "ต้องการลบเอกสาร [ชื่อ]? การกระทำนี้ไม่สามารถย้อนกลับได้"
       │
       └── ยืนยัน
            │
            ▼
       ตรวจสอบสิทธิ์:
         - นักศึกษา: ลบได้เฉพาะ PENDING ของตัวเอง
         - เจ้าหน้าที่: ลบได้ทุกสถานะ
            │
            ▼
       ลบไฟล์ PDF ออกจากระบบ
       ลบ Document record ออกจาก DB
       บันทึก ActivityLog (DOCUMENT_REMOVE)
            │
            ▼
       แสดง Toast "ลบเอกสารสำเร็จ"
       รีเฟรชรายการเอกสาร
```

## 4. Borrowing Status Flow — การยืมเครื่องมือวิจัย

ระบบยืมเครื่องมือวิจัย นักศึกษาเลือกเครื่องมือจากที่มีอยู่ในระบบ + อัปโหลดใบอนุญาต PDF ผ่าน 3 สถานะเช่นเดียวกับเอกสาร

### 4.1 State Machine Diagram

```
                      ┌──────────────────────────┐
                      │                          │
   นักศึกษา            │       PENDING            │
   ส่งคำขอยืม          │      รอตรวจสอบ           │
  ───────────────►    └───────────┬──────────────┘
   + อัปโหลดใบอนุญาต                │
                      ┌──────────┴───────────┐
                      │                      │
                 ┌────▼─────┐          ┌─────▼──────┐
                 │          │          │            │
                 │ APPROVED │          │ REJECTED   │
                 │อนุมัติแล้ว │          │ ปฏิเสธแล้ว   │
                 │          │          │            │
                 └──────────┘          └────────────┘
```

### 4.2 สถานะการยืม (Borrowing Status)

| สถานะ | ชื่อไทย | สี Badge | คำอธิบาย |
|---|---|---|---|
| `PENDING` | รอตรวจสอบ | ส้ม (Amber) | คำขอยืมใหม่ที่รอเจ้าหน้าที่ตรวจสอบ |
| `APPROVED` | อนุมัติแล้ว | เขียว (Green) | เจ้าหน้าที่อนุมัติคำขอยืมแล้ว |
| `REJECTED` | ปฏิเสธแล้ว | แดง (Red) | เจ้าหน้าที่ปฏิเสธคำขอยืมพร้อมเหตุผล |

### 4.3 รายละเอียดการเปลี่ยนสถานะ

| # | จาก | เป็น | ผู้ดำเนินการ | เงื่อนไข | Side Effects |
|---|---|---|---|---|---|
| B1 | — | `PENDING` | นักศึกษา | เลือกเครื่องมือ + อัปโหลดใบอนุญาต PDF | บันทึก ActivityLog (`BORROW_SUBMIT`) |
| B2 | `PENDING` | `APPROVED` | เจ้าหน้าที่ | กดปุ่ม "อนุมัติ" | set `reviewedBy`, `reviewedAt`; บันทึก ActivityLog (`BORROW_APPROVE`) |
| B3 | `PENDING` | `REJECTED` | เจ้าหน้าที่ | กดปุ่ม "ปฏิเสธ" + กรอกเหตุผล | set `reviewedBy`, `reviewedAt`, `adminNotes`; บันทึก ActivityLog (`BORROW_REJECT`) |
| B4 | `PENDING` | (ลบ) | นักศึกษา | ลบคำขอของตัวเองเท่านั้น | ลบไฟล์ใบอนุญาต + ลบ record; บันทึก ActivityLog (`BORROW_REMOVE`) |
| B5 | ทุกสถานะ | (ลบ) | เจ้าหน้าที่ | ลบได้ทุกสถานะ | ลบไฟล์ใบอนุญาต + ลบ record; บันทึก ActivityLog (`BORROW_REMOVE`) |

### 4.4 กฎที่เปลี่ยนแปลงไม่ได้ (Immutable Rules)

- `APPROVED` และ `REJECTED` เป็น **สถานะสุดท้าย** — เปลี่ยนสถานะต่อไม่ได้
- นักศึกษาลบคำขอได้เฉพาะ **PENDING** ของตัวเองเท่านั้น
- เจ้าหน้าที่ลบคำขอได้ทุกสถานะ

### 4.5 Borrow Request Flow (นักศึกษาส่งคำขอยืม)

```
 นักศึกษาเข้าหน้า /borrow
       │
       ▼
 เลือกเครื่องมือวิจัยจากรายการ (รายการมาจากเอกสารที่ถูก APPROVED)
       │
       ▼
 กรอกข้อมูล:
   - ชื่อผู้ขอยืม (requesterName)
   - วันที่ขอยืม (requestDate)
   - รายละเอียดเพิ่มเติม (additionalDetails)
   - อัปโหลดใบอนุญาต PDF (license file)
       │
       ├── [ทางเลือก] กดปุ่ม "OCR" เพื่ออ่านใบอนุญาตอัตโนมัติ
       │       │
       │       ▼
       │   ระบบ OCR อ่านข้อมูลจาก PDF:
       │     - ดึงข้อความด้วย pdftotext
       │     - วิเคราะห์ด้วย AI (ถ้ามีการตั้งค่า)
       │     - กรอกข้อมูลอัตโนมัติ: ชื่อผู้ขอ, วันที่, รายละเอียด
       │
       ▼
 ตรวจสอบข้อมูล:
   ├── ต้องเลือกเครื่องมือ
   ├── ต้องอัปโหลดใบอนุญาต PDF
   └── ไฟล์ PDF ขนาดไม่เกิน 10 MB
       │
       └── ข้อมูลถูกต้อง
            │
            ▼
       สร้าง BorrowingRecord (status = PENDING)
       บันทึกใบอนุญาต: uploads/borrowing/{recordId}.pdf
       บันทึก ActivityLog (BORROW_SUBMIT)
            │
            ▼
       แสดง Toast "ส่งคำขอยืมสำเร็จ"
       รีเฟรชรายการประวัติการยืม
```

### 4.6 แหล่งที่มาของรายการเครื่องมือวิจัย

## 5. Email Notification Flow — การแจ้งเตือนอีเมล

ระบบส่งอีเมลแจ้งเตือนผ่าน CMU Email API (`mis.nurse.cmu.ac.th/thesis/EmailApi`)

### 5.1 สรุปอีเมลทั้งหมด

| # | เหตุการณ์ | ผู้ส่ง | ผู้รับ | Subject | เนื้อหาหลัก |
|---|---|---|---|---|---|
| E1 | นักศึกษาอัปโหลดเอกสาร | ระบบ | เจ้าหน้าที่ (To + CC) | "แจ้งเตือน: นักศึกษาอัปโหลดเอกสารเครื่องมือวิจัย" | ชื่อนักศึกษา, รหัส, รายการเอกสาร |
| E2 | เจ้าหน้าที่อนุมัติ (เอกสารทั้งหมดของนักศึกษาครบแล้ว) | ระบบ | นักศึกษา | "แจ้งผลการพิจารณาวิทยานิพนธ์" | แจ้งว่าเอกสารทั้งหมดอนุมัติแล้ว |
| E3 | เจ้าหน้าที่ปฏิเสธเอกสาร | ระบบ | นักศึกษา | "แจ้งผลการพิจารณาวิทยานิพนธ์" | ชื่อเอกสาร + เหตุผลที่ปฏิเสธ |
| E4 | เจ้าหน้าที่ Bulk Approve | ระบบ | นักศึกษา | "แจ้งผลการพิจารณาวิทยานิพนธ์" | รายการเอกสารที่อนุมัติทั้งหมด |

### 5.2 การจัดการ Email Token

```
 ระบบต้องส่งอีเมล
       │
       ▼
 ตรวจสอบ Email API Token:
   - Token มีอยู่และยังไม่หมดอายุ? → ใช้เดิม
   - Token หมดอายุหรือไม่มี? → ขอ Token ใหม่
       │
       ▼
 เรียก Email API → SendEmail
       │
       ├── สำเร็จ → อีเมลถูกส่ง
       └── ไม่สำเร็จ → บันทึก log error (ไม่ขัดขวางการทำงานหลัก)
```

### 5.3 อีเมลผู้ดูแลระบบ

| สภาพแวดล้อม | To | CC |
|---|---|---|
| Production | `supapan.ch@cmu.ac.th` | `ampika.s@cmu.ac.th` |
| Development | อีเมลสำหรับทดสอบ | — |

### 5.4 กฎการส่งอีเมลแจ้งนักศึกษา (Approve)

```
 เจ้าหน้าที่อนุมัติเอกสาร 1 ฉบับ
       │
       ▼
 ตรวจสอบ: นักศึกษาคนนี้ยังมีเอกสาร PENDING เหลืออยู่หรือไม่?
       │
       ├── มี PENDING เหลือ → ยังไม่ส่งอีเมล
       │   (รอให้อนุมัติหมดทุกฉบับก่อน)
       │
       └── PENDING หมดแล้ว → ส่งอีเมล 1 ฉบับแจ้งนักศึกษา
           (กัน spam อีเมล — ส่งครั้งเดียวเมื่อเสร็จทั้งหมด)

 ข้อยกเว้น: ถ้าเจ้าหน้าที่ปฏิเสธ → ส่งอีเมลทันทีทุกครั้ง
```

## 6. Activity Log — ประวัติการใช้งาน

ระบบบันทึกกิจกรรมทุกครั้งที่เกิดการเปลี่ยนแปลง เพื่อการตรวจสอบย้อนหลัง (Audit Trail)

### 6.1 รายการ Action ทั้งหมด

| # | Action | ชื่อไทย | เกิดเมื่อ | ข้อมูลที่บันทึก |
|---|---|---|---|---|
| 1 | `USER_LOGIN` | เข้าสู่ระบบ | ผู้ใช้ล็อกอินสำเร็จ | ผู้ใช้ |
| 2 | `DOCUMENT_UPLOAD` | อัปโหลดเอกสาร | นักศึกษาอัปโหลดเอกสาร | ผู้ใช้, เอกสาร, ชื่อเครื่องมือ |
| 3 | `DOCUMENT_APPROVE` | อนุมัติเอกสาร | เจ้าหน้าที่อนุมัติเอกสาร | ผู้ดำเนินการ, เอกสาร, นักศึกษา |
| 4 | `DOCUMENT_REJECT` | ปฏิเสธเอกสาร | เจ้าหน้าที่ปฏิเสธเอกสาร | ผู้ดำเนินการ, เอกสาร, เหตุผล |
| 5 | `DOCUMENT_REMOVE` | ลบเอกสาร | นักศึกษาหรือเจ้าหน้าที่ลบเอกสาร | ผู้ดำเนินการ, เอกสาร |
| 6 | `BORROW_SUBMIT` | ส่งคำขอยืม | นักศึกษาส่งคำขอยืมเครื่องมือ | ผู้ใช้, เครื่องมือ |
| 7 | `BORROW_APPROVE` | อนุมัติคำขอยืม | เจ้าหน้าที่อนุมัติคำขอยืม | ผู้ดำเนินการ, คำขอยืม |
| 8 | `BORROW_REJECT` | ปฏิเสธคำขอยืม | เจ้าหน้าที่ปฏิเสธคำขอยืม | ผู้ดำเนินการ, คำขอยืม, เหตุผล |
| 9 | `BORROW_REMOVE` | ลบคำขอยืม | นักศึกษาหรือเจ้าหน้าที่ลบคำขอยืม | ผู้ดำเนินการ, คำขอยืม |

### 6.2 ข้อมูลที่บันทึกใน ActivityLog

| ฟิลด์ | คำอธิบาย | ตัวอย่าง |
|---|---|---|
| `action` | ประเภทกิจกรรม | `DOCUMENT_APPROVE` |
| `userId` | ผู้ดำเนินการ | `cmu-12345` |
| `targetType` | ประเภทข้อมูลเป้าหมาย | `Document`, `BorrowingRecord` |
| `targetId` | ID ของข้อมูลเป้าหมาย | `clx1abc123` |
| `targetLabel` | ข้อความอธิบายเป้าหมาย | "สมชาย → The Positive Discipline Questionnaire" |
| `createdAt` | เวลาที่เกิดกิจกรรม | `2026-05-28T10:30:00Z` |

### 6.3 การดู Activity Log

- เจ้าหน้าที่สามารถดูได้ที่ `/admin/activity-log`
- รองรับ: ค้นหา, กรองตามประเภท, กรองตามช่วงวันที่
- ใช้ Backend Pagination (ไม่โหลดข้อมูลทั้งหมดในครั้งเดียว)

## Student Status (จาก CMU MIS API — แสดงผลเท่านั้น)

ไม่ใช่ state machine — เป็นข้อมูลจากระบบของมหาวิทยาลัย แสดงผลเพื่อให้เจ้าหน้าที่เห็นสถานะนักศึกษาเท่านั้น:

| สถานะ | ชื่อไทย | สี Badge |
|---|---|---|
| Active | กำลังศึกษา | เขียว |
| Resigned | ลาออก | เทา |
| Dismissed | พ้นสภาพ | แดง |
